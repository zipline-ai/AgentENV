## Proposed protocol and descriptor (pending field 1)

Protocol identifier: `agentenv-process-epoch-v1`. A descriptor contains `protocol`, `node_id`, `node_incarnation`, `runtime_id`, `runtime_incarnation`, `guest_boot_id`, `enrollment_revision`, `process_endpoint`, `guest_build_sha256`, `capabilities_sha256`, and `managed=true`. UUID coordinates use canonical lower-case strings; hashes are lower-case SHA-256 hex. Descriptor and receipt responses are authenticated evidence, not unsigned strings returned by a capability probe.

### Trust chain and roots

The following provisioning is proposed, not present in the current fork. It is a release dependency with tests, not an assumed property of the existing fleet API key.

| Hop / issuer | Source of authority and verification |
| --- | --- |
| Lifecycle → node | A dedicated app `ProcessEpochAuthorityIssuer` signs only a captured, committed dispatch of the exact saved creation/transition. It binds its operation, immutable canonical bytes/hash, tenant/family/sandbox, A and reserved B, launch, route, runtime/incarnations, descriptor digest and expiry. The lifecycle owner must implement the issuer facet; a DTO, browser actor or arbitrary caller string cannot invoke a raw signing endpoint. Read-only lookup authority comes from the saved operation, never a new dispatch claim. |
| Controller → node enrollment | An operator-managed provider enrollment authority issues a short-lived node certificate for the authenticated provisioned VM identity and a newly registered node-process incarnation. Registration uses the VM's workload identity checked against the provider's provisioned instance inventory. The app validates the provider CA, exact node certificate identity, current enrollment revision and saved route through mTLS; neither DNS nor an API-key-authenticated JSON node ID is enough. |
| Node → guest | The node verifies the selected read-only tools artifact against the operator-signed release manifest before mapping it into the exact VM. It creates a per-boot guest channel key/certificate bound to the hypervisor runtime handle, runtime incarnation, boot ID and enrollment revision. Provision over the host-controlled guest-init channel, outside user credentials; restrict enrollment to that handle, never an endpoint from a request. The private channel key is per boot, not baked into a template. The guest checks the enrolled node certificate and the controller signature before admission. |
| Guest → node → lifecycle | Guest receipts are signed with that enrolled guest key, including the complete binding, original request hash, journal revision and receipt body. The node validates the signature, current exact guest enrollment and expected build manifest, fsyncs its mirror, then signs a response envelope binding that guest receipt/digest, node incarnation/revision and the caller's lookup nonce. Lifecycle verifies the provider chain, saved node/guest enrollments, both signatures, nonce, request hash and expected descriptor/build against its saved authority before accepting evidence. Historical first receipts retain their original signatures; a fresh signed lookup envelope reports their current reconciled status without rewriting them. |

This is provider-controlled authentication and verified provisioning, not hardware attestation. The threat model trusts the controller, host/hypervisor and release authority; a compromised host or privileged guest that can replace the managed server is not made trustworthy by a signed self-report. Managed guests cannot retain user-accessible root/sudo paths that replace the verifier, trust bundle, journal or policy. If the current image cannot enforce this boundary, capability advertisement and activation remain blocked pending a reviewed image-policy change. Do not silently claim the current image provides it.

The operator creates separate Ed25519 controller-authorization and provider-enrollment/release roots through the approved secret-management provisioning process. Private roots and controller signing keys live in the controller/operator secret store, never a guest image or user credential volume. Node private keys live in host-only storage; guest boot keys and managed policy are supplied through the host-controlled read-only tools/init channel. App trust bundles pin provider roots and approved manifest hashes; host bundles pin controller and release roots. The guest receives the controller/provider public trust bundle and managed policy from verified read-only tools provisioning. `/init`, restored local configuration and ordinary envd access-token setup cannot unset managed mode or replace that bundle.

Use distinct signed-envelope domains/audiences: `process-epoch/descriptor/v1`, `seal/v1`, `bind/v1`, `lookup/v1`, `initializer/v1`, `mutation/v1`, `stream-open/v1`, `frame/v1`, `guest-receipt/v1`, and `node-response/v1`, each prefixed by `agentenv-process-epoch`. Audience also names the exact receiving node or guest enrollment. Initializer authority binds a saved creation dispatch and a finite approved bootstrap operation set; it cannot bind a funded epoch or act as a general process token. Bind and initializer DTOs still require joint agreement (fields 3/7).

Key rotation is an explicit operator trust-bundle revision: distribute new public keys before issuing with them, retain old verification keys for historical receipts, and require a fresh nonce-bound response from a currently enrolled node. The issuer stops new grants when a key is revoked, and lifecycle rejects current evidence under that revoked enrollment/trust revision. Provider revocation also uses the execution exclusion to close admission and drain or retain admitted work; its acknowledgement is not complete until the exact guest fence is proven. During a lost or incomplete revocation acknowledgement, lifecycle permits no replacement epoch and retains the unresolved work obligation. Unknown or stale revision checks fail closed; the plan does not claim a disconnected guest instantly observes a controller key change. Historical signatures remain audit evidence, never current work authority after revocation. Revoked boot/node keys cannot enroll replacements or mint fresh receipts. Missing keys, unverifiable rotation and expiry retain obligations; they do not reset the epoch or authorize redispatch. No production secret names/values or rollout are assumed by this plan.

Build evidence is pinned independently: the signed release manifest records the full envd source commit, ordered patch hashes, protocol descriptor digest and actual compiled binary/tool-image hashes. The app's approved release policy and node's verified artifact mapping must agree before the guest handshake is considered. The node attests what it provisioned over its authenticated provider identity; the guest's reported build value is checked against that evidence and is never the trust root.

## Seal request, receipt and outcomes (pending field 2)

The proposed immutable binding is: `protocol`, `tenant_id`, `sandbox_family`, `sandbox_id`, `transition_id`, `launch_id`, `expected_session_id`, `reserved_session_id`, all descriptor coordinates, and `operation_id`. Canonical request bytes are a fixed-order UTF-8 JSON object with no maps, unknown fields, alternate UUID spellings or duplicate keys. Store the exact original bytes and SHA-256; golden vectors define encoding across implementations. The outer signed envelope carries that digest; no circular hash field occurs inside its own input. A changed byte sequence under the same operation ID conflicts.

`SealProcessEpoch` closes admission for expected A under the same gate used at final execution. Under that exclusion, close new admissions and freeze the complete admitted process/mutation/stream inventory and its digest. Persist closing intent before acknowledging receipt of the close request. That acknowledgement is only `accepted/incomplete`, never sealed/drained success; queued operations must reacquire/check admission, not wait through the seal and execute in B. Track all admitted work until it finishes or is conclusively canceled. No SQL lock or provider network call is part of this guest exclusion.

Receipt fields: immutable binding, `request_sha256`, `receipt_id`, `state` (`sealed` or `incomplete`), `execution_outcome` (`drained`, `scope_retired`, `unknown`), and `affected_operations_sha256`. The digest covers the sorted exact process/mutation/stream inventory frozen under the execution exclusion, not PIDs. No admission can occur between closing the gate and freezing that inventory. A successful receipt requires no unresolved admitted work or effects in that inventory. Persist the first completed receipt before returning it. An incomplete observation is not a successful receipt and cannot authorize bind. Later lookup may observe a subsequently proven terminal receipt; it cannot rewrite one already committed.

A successful stdin write, tcdrain, empty socket buffer or closed stream does not establish that a program consumed PTY input. V1 will conservatively return `incomplete/unknown` for any affected live scope with unproved queued input or continuing effects. It will not kill processes to obtain success. `scope_retired` requires separate explicit captured retirement authority plus real proof that the exact affected process scope has ended; siblings and history are preserved. Processes that escape the provable scope keep the result unknown. This deliberately leaves retained interactive-process handover unavailable until codex-9 and the reviewer approve an implementable retirement/drain policy.

## Lookup, storage and restart (pending field 4)

Proposed node endpoints: POST `/sandboxes/{runtime_id}/process-epochs/seal`, POST `/sandboxes/{runtime_id}/process-epochs/bind`, and GET `/sandboxes/{runtime_id}/process-epoch-operations/{operation_id}`. Guest controls use typed ProcessEpoch RPCs with the identical authority binding. The node checks the saved runtime/incarnation and forwards only to the saved endpoint. Neither node nor gateway may schedule, resume, resolve a newer runtime or redispatch a mutation to answer lookup.

### Durable records and authority outside guest snapshots

The authoritative non-rollback anchor is the node's fsynced host `process_epoch` ledger, outside all guest disks/memory snapshots. Its key is `(controller_identity, tenant_id, runtime_id, runtime_incarnation)`, with monotonically increasing `enrollment_revision`, current node/guest incarnations, current epoch/phase, frozen inventory digest and append-only operation/receipt hashes. An operation key adds `(operation_id, request_sha256)`; a stream-frame key adds `(stream_id, sequence)`. Accepted identities remain tombstones indefinitely. Loss or corruption of this ledger is unavailability, not first enrollment. No automatic host-ledger reset or restore from an older backup is allowed.

Lifecycle also retains the saved enrollment revision and receipt digest with its transition. A node mirror older than that saved anchor cannot be accepted. Rebuilding a lost host ledger requires a separately reviewed evidence recovery procedure; it is unavailable in this cut. Neither a guest snapshot nor a restarted node may manufacture its replacement. Operator restoration of host metadata without a proven current anchor keeps the node quarantined.

The guest has an fsynced journal keyed by the same binding and enrolled boot revision. A per-runtime reconciliation mutex serializes node seal/bind/enrollment/lookup state transitions. Guest execution exclusion serializes local reconciliation with admission and effects. Do not hold the guest exclusion over node network calls: publish closed state locally, release the lock, collect external evidence, then conditionally install only if the captured revision and closed phase still match. Competing reconciliation attempts CAS the same external revision; only one can publish a new enrollment. The loser returns the saved result or unavailable, never a second operation.

### Transition and fsync order

| State / transition | Required ordering and response |
| --- | --- |
| `unreconciled` | Every guest/server startup and restored instance starts unavailable. Node refuses process forwarding until exact enrollment reconciles. A snapshot known to contain an open gate or unresolved process effects is not eligible for managed restore; no claim is made that network isolation stops already queued PTY commands. Only a proven closed/quiesced snapshot can enter this path. |
| `open(A)` → `closing(A, transition, inventory)` | Node first fsyncs the exact close intent against current enrollment/A. Guest closes admission and freezes inventory under exclusion, fsyncs closing intent, then returns accepted/incomplete. Node fsyncs that observation. A timeout never returns either copy to open. |
| Mutation `accepted` → `execution_claimed` | Node fsyncs the immutable operation/frame identity and grant against open A before delivery. Guest fsyncs the matching one-use claim, then rechecks binding and gate at the effect boundary. The operation remains in the frozen seal inventory if it was admitted before closing. |
| `execution_claimed` → `effect_unknown` or `completed` | After an effect, guest fsyncs exact completion evidence before reply; node fsyncs its mirror before acknowledging completion. Any crash/partial effect without conclusive completion records effect_unknown. A claimed operation is never re-executed to discover its outcome. A completed byte write alone does not prove PTY drain. |
| `closing` → `completed_seal` | Guest proves every frozen inventory member drained or separately authorized and conclusively retired, fsyncs the first signed terminal receipt, then node validates and fsyncs the exact receipt mirror. Only the mirrored authenticated terminal receipt can be returned as successful seal. Incomplete is never promotable by a timeout or by node inference. |
| `completed_seal` → `bind_pending(B)` → `bound(B)` | Node fsyncs bind intent conditioned on exact A/transition/completed-seal receipt. Guest verifies that intent, fsyncs its conditional binding and receipt while still closed. Node fsyncs the identical receipt and bound revision. Guest may publish open B only after validating the node's commit acknowledgement and CASing its still-closed matching binding; it fsyncs that publication. Lost acknowledgement leaves it closed. This provider state alone does not publish a billable B; the lifecycle installation remains field 7. |
| Receipt lookup | Returns the first immutable completed receipt only when current enrollment reconciliation supports it, inside a fresh authenticated response. Claimed/closing/partial state returns accepted/incomplete with no usable seal/bind receipt. A genuinely absent exact operation returns fixed 404. Missing/corrupt authority storage or mismatched copies returns unavailable/unknown, not 404. All are read/evidence recovery paths, never effect redispatch. |

Fresh boot enrollment is node-controlled. Before incrementing the external enrollment revision, the node must prove the old exact VM/process-server incarnation cannot execute or accept work; unknown stop/fence evidence blocks enrollment. Bind the new host-injected channel identity to the saved exact runtime/boot and approved tools artifact. Fence prior channels and trust revisions; reconcile the closed guest journal to the external ledger before publishing the new descriptor. A fresh boot UUID by itself is not proof that the older boot stopped. This enrollment requires the lifecycle owner's captured transition/creation authority and is not permitted to create a new funded session.

### Restart / rollback matrix

| Observed copies | Recovery and lookup result |
| --- | --- |
| Guest completion ahead of node mirror | Read the exact signed guest receipt under the existing external claim, verify the current boot and hash chain, then CAS/fsync the missing mirror. Return the same receipt; never rerun its operation. |
| Node intent/claim ahead of guest | Keep closed or mark effect_unknown. Absence of guest claim is not proof no effect occurred. Return incomplete; do not deliver the mutation again. |
| Node completed receipt ahead of guest journal | Treat as rollback/corruption, quarantine the guest and return unknown. Never copy bound B into a stale guest and open it. Historical node evidence is retained for authorized recovery. |
| Lost claim or receipt reply | Exact lookup returns the durable state/first receipt. Lost claim with no conclusive receipt stays unknown; no new key, frame or operation is minted. |
| Snapshot rollback after B | External enrollment/epoch/journal revision exceeds snapshot state: refuse managed restore/publication. Keep the external B record and obligation; no reopening A, resetting the journal or inventing C. |
| Missing/corrupt guest or host storage | Quarantine and preserve whatever evidence exists; no success, initial bind or journal reset. Exact recovery outside this cut is required. |
| Two concurrent reconciliations | Both start closed; serialize/CAS the same external enrollment revision and guest closed revision. One commits; the other returns identical proven evidence or unavailable. Neither performs new effects. |

Crash tests stop real processes between every fsync, provider delivery, effect, guest completion, node mirror and guest publication boundary. Restart with the same files and with older guest snapshot files; assert the matrix outcomes, immutable receipts and zero duplicate effects. Scope retirement after unknown remains a separately authorized operation, not a lookup side effect.

## Execution and bind fencing (pending field 5)

Each process has a unique `process_operation_id`; each unary mutation has its own `operation_id`, immutable digest and epoch binding. Registry lookup is exact, never PID/tag search. Seal and final spawn/write/signal/resize/close share exclusion. Long writes must support cancellation and bounded drain; failure to prove cancellation leaves the epoch closed and incomplete. The seal transport deadline cannot turn incomplete work into success or reopen A.

A stream first performs authenticated `OpenProcessStream` admission. Its immutable record binds `stream_id`, tenant/family/sandbox, node/runtime/boot enrollment, funded epoch, exact process operation, terminal incarnation, permitted direction/operation (`stdin`, `pty-input`, or `output-only`), and the captured opening authority/hash. Both the opening and every subsequent frame must be authorized; a frame token cannot create a stream. Reconnecting references the same saved stream record and epoch, never migrates A to B. Output-only Connect receives explicit captured read authority and cannot gain mutation authority from successful attachment.

Frames contain the original stream ID, monotonically increasing sequence starting at 1, immutable mutation ID, payload length and payload digest. Persist acceptance and the next expected sequence before execution. Only the next frame may execute, under the original binding and current gate; a gap/reordering is denied without writing. A duplicate sequence with identical bytes returns its first durable outcome without another write; changed bytes or mutation ID conflicts. Keep claimed/completed frame records, including empty or keepalive frames as non-effect protocol messages with their permitted type, so a reconnect cannot reset ordering.

A partial write makes that frame `effect_unknown`, closes input admission for the stream, and blocks all later sequences. Report no success or consumed-byte inference. Retrying cannot split, reframe or assign new identities to its old payload: the node/guest only accept grants for the saved outstanding frame; captured client recovery reuses it. Opening a replacement stream/process to bypass unresolved input requires separately reviewed lifecycle authority and conclusive retirement, not a generic retry option. Identical text intentionally sent later is not deduplicated by content; its new authority must be independently granted after the prior operation is resolved.

Every frame reproves the immutable open binding immediately before its write while holding execution exclusion. Seal closes stream admission, freezes accepted frame inventory and invalidates output subscriptions under that same exclusion. Frames queued before seal but not admitted fail; admitted partial writes keep seal incomplete. A reconnect cannot re-enable them in B.

Output chunks carry original epoch/process/terminal/stream coordinates plus sequence. Authorization applies at output-only open and before forwarding each chunk; seal invalidates the subscriber generation under the execution exclusion, so later queued chunks are dropped. Socket send acceptance before seal is already-delivered history, not revocable output. Node and app completion checks reject late A chunks before disclosure; the app discards its unforwarded A buffer and never replays it through B. No history rewrite is attempted. Do not hold the exclusion across an indefinitely blocking network flush: bounded subscriber queues register admission at forwarding, cancellation closes them at seal, and any unproved in-flight disclosure remains unavailable to the B consumer.

`BindProcessEpoch` performs an atomic expected-A/transition/seal-receipt comparison before publishing reserved B. No queued A operation is carried into B. Exact replay returns the original receipt; changed scope or seal conflicts. Initial bind is a separate operation requiring saved creation authority and an unused exact guest incarnation. The request/receipt fields for first bind and the lifecycle publication transaction are pending joint contract items 3 and 7; implement no success stub while those are unresolved.

Managed guests deny the old PID/tag process mutation paths even through direct envd access. Audit initializer/bootstrap process starts as separate authority: managed boot cannot silently use an unrestricted legacy initialization path. Ordinary unmanaged guests keep their current protocol. Output chunks retain epoch, process operation and terminal incarnation; seal cancels the old subscribers. App-buffered output invalidation is codex-9's participant and remains required before consumers activate.

## Implementation and tests

One fork implementation PR with reviewable commits: (1) pinned source/build manifest and typed protocol with invalid-descriptor tests; (2) durable guest operation registry plus seal/bind exclusion and real process tests; (3) authenticated exact node/gateway forwarding, restart reconciliation and hard CI job. If the guest patch cannot be reviewed as one PR, split after the dormant protocol/registry commit; neither partial cut advertises a usable capability. App registration/composition is a later jointly reviewed PR after the contract pending list is empty.

Write red tests before enforcement. These named proofs from the versioned contract are commitments, not existing passing tests:

- `TestProcessEpochSealOrdersEveryMutation`: real child processes and PTYs; barriers before admission and immediately before the actual effect; both orders for spawn, stdin, signal, resize, close, and queued stream frames. Assert exact operation IDs and zero denied effects.
- `TestProcessEpochUnknownPTYDrainRefusesBind`: unread PTY bytes and blocked writes keep B unavailable; exact tmux sibling remains alive and history unchanged. No sleep-based ordering or tcdrain inference.
- `TestProcessEpochExactOperationReplay`: same operation returns first receipt; changed bytes/scope/epoch/incarnation denied; kill server after claim and after effect, reopen journal, lose replies, and prove no duplicate spawn or PID fallback.
- `TestProcessEpochRestoredGuestAndProxyBypassDeny`: wrong build, unsupported guest, stale snapshot ledger, direct envd, proxy host/path and gateway fallback all deny; zero resume/scheduler calls.
- `TestProcessEpochOutputDoesNotCrossSeal`: real output-only Connect and input-stream barriers, hold output before forwarding across seal, then release; no A chunk reaches B, prior displayed history retained. Codex-9 supplies the app half.
- `TestProcessEpochStreamReplayAndPartialWrite`: real pipe/PTY capacity barrier forces partial write; exact duplicate sequence never writes twice, changed bytes and reordered frames deny, seal between accepted frames rejects queued input, lost acknowledgements cannot reframe or reopen the stream.
- `TestProcessEpochTrustChainDenials`: real signed request/response fixtures with missing/rotated/revoked keys, wrong node/boot/audience, forged descriptor/receipt, mismatched independently pinned artifact, and restored writable trust material. All make zero managed effects and no funded publication.
- `TestProcessEpochRestartReconciliationMatrix`: crash at each durable/effect boundary in the table, restore older journal files, corrupt/remove each ledger, race two reconciliations; exact receipt stays immutable and mismatches never enable work.

CI must execute the patched guest binary with real process/PTY/tmux fixtures, not only mocked Rust clients. Run guest Go tests with race detection, Rust build/tests/clippy, gateway tests/race, protocol generation drift checks and image build. Fork Actions' pending admin opt-in blocks PR READY, not this plan. Local logs are interim evidence. Build/import/select and live operations remain coordinator-owned.
